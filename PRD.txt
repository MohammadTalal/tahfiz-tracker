# Quran Learning & Memorization Platform
## Master Product Requirements Document, Technical Architecture, Database Design, and Implementation Plan

**Project name:** Working title — Quran Learning Platform  
**Product type:** Multi-tenant web application / SaaS  
**Primary users:** Mosque administrators, Quran teachers, students, and parents/guardians  
**Initial target market:** Mosques, Quran memorization programs, Islamic schools, and independent Quran teachers  
**Initial business model:** Free to use, with the possibility of non-intrusive advertising or sponsorship in the future  
**Development approach:** AI-assisted development using Claude Code  
**Document status:** Initial master specification  
**Primary objective:** Build a secure, reliable, maintainable, mobile-friendly platform for managing Quran memorization, revision, student progress, and parent communication.

---

# 1. Project Vision

Build a modern web platform that helps Quran teachers manage their students' memorization and revision progress while allowing parents to follow their children's learning journey.

The platform must support multiple independent organizations. Each organization may represent a mosque, Quran school, memorization program, Islamic center, or another educational group.

Each organization has its own administrator, teachers, classes, students, and parent relationships.

The platform must make it easy for a teacher to complete the administrative work associated with a Quran lesson in as little time as possible.

The core workflow should be:

1. An administrator creates an organization and configures its program.
2. The administrator invites teachers.
3. Teachers create classes and enroll students.
4. Teachers record each student's new memorization, revision, performance, and next assignment.
5. Parents can access their children's progress through their own accounts.
6. Students can view their assignments and learning history.
7. Administrators can monitor the organization's overall progress and generate reports.

The platform should prioritize usability, data security, accessibility, and low operating costs.

## 1.1 Product principles

- Quran memorization and revision are the primary features.
- Recording a lesson should be fast and straightforward.
- The interface must support Arabic and right-to-left layouts from the beginning.
- Every organization must have strictly isolated data.
- Parents must only access children for whom they have been explicitly authorized.
- Teachers must only access students and classes they are authorized to manage.
- Student records must remain available when a student changes teachers or classes.
- Parent accounts must be optional for a student's initial enrollment.
- The platform must work well on mobile phones, tablets, and desktop browsers.
- The initial version must be free of unnecessary complexity.
- The system should be designed to support future growth without requiring a complete rewrite.

## 1.2 Definition of success

The initial release should allow a real Quran teacher to manage a class without relying on spreadsheets or paper records for routine memorization tracking.

Speed target: a teacher should be able to record a typical lesson in under 30 seconds on a phone.

Success should be measured by:

- Time required to record a lesson.
- Percentage of teachers who continue using the platform after a trial period.
- Number of active students.
- Percentage of parents who activate their accounts.
- Accuracy and completeness of memorization records.
- Frequency of teacher and parent engagement.
- Reliability and security of the platform.

Do not assume commercial success merely because the application has been built. Validate the product with actual teachers and parents.

# 2. Technology Stack

Use the following technologies unless a concrete technical limitation is identified.

## 2.1 Frontend

**Framework:** Next.js with the App Router  
**Language:** TypeScript with strict type checking  
**UI library:** React  
**Styling:** Tailwind CSS  
**UI components:** shadcn/ui  
**Icons:** Lucide React  
**Form handling:** React Hook Form  
**Schema validation:** Zod  
**Server-side data access:** Next.js Server Components and server-side service modules  
**Client-side interactivity:** React Client Components only when needed

Use the latest mutually compatible stable releases at the start of development. Pin dependencies and use a lockfile rather than automatically upgrading packages during implementation.

Use TypeScript throughout the application. Avoid `any` except when strictly necessary and documented.

## 2.2 Backend and data services

**Database:** Supabase PostgreSQL  
**Authentication:** Supabase Auth  
**File storage:** Supabase Storage, only when required  
**Database access:** Supabase-supported server and client libraries  
**Authorization:** PostgreSQL Row Level Security (RLS), supplemented by server-side authorization checks  
**Database schema changes:** Version-controlled SQL migrations  
**Validation:** Zod schemas and PostgreSQL constraints

Do not introduce a separate backend service initially. Use Next.js server-side functionality together with Supabase.

Do not put database service-role keys or other privileged secrets in browser-accessible code.

## 2.3 Hosting and development tools

- **Application hosting:** Vercel or a compatible hosting provider.
- **Database and authentication hosting:** Supabase.
- **Source control:** Git and GitHub.
- **AI coding assistant:** Claude Code.
- **Unit and component tests:** Vitest and React Testing Library.
- **End-to-end tests:** Playwright.
- **Code quality:** ESLint and TypeScript checks.
- **Formatting:** Prettier.
- **Error monitoring:** Introduce a suitable monitoring service when needed, subject to privacy requirements.

## 2.4 Why this stack?

Next.js provides a unified React application with server-side capabilities. Supabase reduces the amount of infrastructure that must be built and maintained. PostgreSQL supports relational data, reporting, transactions, and strong access controls.

This combination is appropriate for an initial SaaS platform, provided its authorization rules are designed and tested carefully.

Do not add microservices, Kubernetes, Redis, a separate backend framework, or an independent mobile application unless a demonstrated requirement justifies them.

## 3.2 Architectural requirements

1. Separate UI components from business logic.
2. Separate data-access functions from presentation code.
3. Use shared validation schemas for important forms and operations.
4. Avoid duplicating authorization logic across pages.
5. Never trust organization IDs, role names, or student IDs supplied by a browser without verifying access.
6. Use database transactions or suitable atomic operations when a workflow modifies multiple related records.
7. Store database schema changes as migrations in source control.
8. Keep all secrets in environment variables managed by the deployment environment.
9. Avoid unnecessary abstractions and overengineering.
10. Document important architectural decisions.

# 4. Multi-Tenant Organization Model

This is one of the most important architectural requirements.

The platform must support multiple independent organizations on the same application and database.

Examples:

- A mosque with five teachers and 80 students.
- An Islamic school with several classes.
- A Quran memorization program operating during weekends.
- An independent teacher managing a small group.
- A teacher working for more than one organization.

## 4.1 Organization

Each organization must have:

- Unique ID.
- Name.
- Optional description.
- Organization type.
- Logo URL, optional.
- Preferred language.
- Time zone.
- Contact email, optional.
- Contact phone, optional.
- Address, optional.
- Status: active, suspended, or archived.
- Creation date.
- Last update date.

An organization may configure its name and other permitted settings.

## 4.2 Organization isolation

Every organization-owned record must be associated with the appropriate organization, directly or through a verified relationship.

A user belonging to Organization A must never access Organization B's private data merely by changing a URL, form field, API request, or database identifier.

Enforce isolation through:

- PostgreSQL RLS.
- Server-side authorization checks.
- Organization membership verification.
- Validated relationships between records.
- Tests that explicitly attempt cross-organization access.

Do not rely only on hiding buttons or pages in the frontend.

## 4.3 Multiple organizations per user

The database must not assume that a user belongs to only one organization.

A teacher may belong to two mosques. A parent may have children enrolled in different programs. A user may have different roles in different organizations.

Store roles on organization memberships or other appropriate scoped relationships rather than as a single global role on the user profile.

# 5. User Roles and Permissions

The platform must support the following roles.

## 5.1 Platform Super Administrator

This is the internal operator of the platform, not the administrator of an individual mosque.

Responsibilities:

- View platform-level operational statistics.
- Manage organization status when necessary.
- Handle abuse and support requests.
- Investigate operational issues using appropriately restricted access.
- Manage platform configuration.

Requirements:

- This role must not be available through ordinary public registration.
- It must not be granted simply because a user creates an organization.
- Access must be tightly controlled and audited.
- Do not build unrestricted access to children's records as a convenience feature.
- Support workflows must use the minimum necessary access.

A separate platform-wide administrative interface can be implemented after the core product is operational.

## 5.2 Organization Administrator / Supervisor

Responsibilities:

- Manage organization settings.
- Invite and manage teachers.
- Create and manage classes.
- Enroll students.
- Assign teachers to classes and students.
- Manage parent invitations and authorized relationships.
- View organization-level reports.
- Review memorization progress.
- Manage organization memberships.
- Archive records according to approved retention rules.

An organization administrator should not automatically become the parent or teacher of every student.

## 5.3 Teacher

Responsibilities:

- View assigned classes.
- View authorized students.
- Record memorization lessons.
- Record revision work.
- Assess performance.
- Assign upcoming memorization.
- Assign revision.
- Record attendance, if enabled.
- Review student history.
- Add educational notes.
- View reports for authorized students.

Teachers must not be able to:

- Change organization ownership.
- Manage platform-wide settings.
- Access unrelated organizations.
- Read private records belonging to students outside their assigned scope.
- Change their role to administrator.

## 5.4 Student

Student accounts are optional in the initial release.

A student account can:

- View assigned memorization.
- View revision tasks.
- View completed lessons.
- View permitted teacher feedback.
- See personal progress.
- Mark a task as practiced or completed when that functionality is enabled.

A student's self-reported completion must not automatically count as a teacher-verified memorization result.

For younger children, avoid unnecessary personal information and keep the interface simple.

## 5.5 Parent / Guardian

A parent account can:

- View each linked child's progress.
- Switch between linked children.
- View completed memorization lessons.
- View upcoming assignments.
- View revision tasks.
- Read teacher feedback intended for parents.
- View permitted attendance information.
- Receive progress notifications when enabled.
- Manage their own notification preferences.

A parent must not be able to:

- Access another family's students.
- Change a teacher's assessment.
- Modify a student's memorization history.
- Assign lessons on behalf of the teacher.
- Access organization administration unless separately authorized.

## 5.6 Permission matrix

| Capability | Platform admin | Organization admin | Teacher | Student | Parent |
|---|---|---|---|---|---|
| Manage platform | Yes | No | No | No | No |
| Manage organization settings | Restricted | Yes | No | No | No |
| Invite teachers | Support only | Yes | No | No | No |
| Manage classes | Support only | Yes | Assigned scope only | No | No |
| Record verified memorization | No by default | If explicitly authorized | Assigned students | No | No |
| View student progress | Restricted support access | Organization scope | Assigned scope | Own records | Linked children |
| View assignments | Authorized support only | Organization scope | Assigned scope | Own assignments | Linked children |
| Manage parent links | Restricted support access | Yes | Limited if authorized | No | Accept or verify invitation |
| Change teacher assessment | No by default | Audited administrative correction | Authorized records | No | No |

All permissions must be enforced by the backend and database policies, not merely by the user interface.

# 6. Authentication and Account Management

## 6.1 Authentication

Use Supabase Auth.

Support:

- Email and password registration where appropriate.
- Email verification.
- Secure login and logout.
- Password reset.
- Session management.
- Protected application routes.
- Invitation-based onboarding.
- Account deactivation and deletion workflows where legally appropriate.

Do not implement your own password storage.

Never store plaintext passwords.

## 6.2 Registration options

The initial application should support these entry paths:

### Path A: Organization administrator

1. User registers.
2. User verifies their email.
3. User creates an organization.
4. The system creates the organization membership with the administrator role.
5. The user may select "I am also a teacher". If selected, the system also creates a teacher membership in the same step.
6. The user enters the organization dashboard.
7. The user can invite teachers.

This supports independent teachers who run their own small group and act as both administrator and teacher. Their setup should take a single short flow.

### Path B: Invited teacher

1. Administrator creates an invitation.
2. The teacher receives an invitation link.
3. The teacher signs in or creates an account.
4. The system verifies the invitation.
5. The teacher joins the correct organization with the intended role.
6. The invitation is marked as accepted.

### Path C: Parent

1. Teacher or administrator initiates a parent invitation for a specific student.
2. The parent receives a secure invitation.
3. The parent signs in or creates an account.
4. The parent verifies the invitation.
5. The system establishes the authorized parent-student relationship.
6. The parent can view the child's permitted information.

### Path D: Student

Student account creation is optional.

The system should support student records without requiring students to have login credentials.

If student accounts are enabled, use a controlled enrollment process and apply additional safeguards for minors.

## 6.3 Invitations

Invitations must:

- Use cryptographically secure, unpredictable tokens.
- Expire after a configurable period.
- Be single-use.
- Be associated with the intended organization and role.
- Be associated with the intended student when applicable.
- Be invalidated when revoked.
- Avoid exposing private student information in URLs.
- Be validated on the server before any relationship is created.

Store only a secure hash of the invitation token when practical.

Invitation delivery:

- Many parents communicate mainly through WhatsApp or phone, not email.
- Email delivery must be optional.
- The issuer must be able to copy a secure invitation link and share it through WhatsApp, a phone's messaging app, or a QR code.
- Shared links follow the same expiry, single-use, revocation, and server-side validation rules as emailed invitations.
- Shared links must not contain the student's name or other private information.

Do not allow an invitation to grant a more privileged role than the issuer is authorized to assign.

# 9. Quran Reference System

The platform must have a reliable way to identify Quran passages.

## 9.1 Reference structure

A Quran passage is a range from a starting point to an ending point. A passage may cross surahs.

Each passage must support:

- Starting surah number.
- Starting ayah number.
- Ending surah number.
- Ending ayah number.
- Surah names in Arabic and English for display.
- Optional display text for a selected passage.

Store canonical references using numeric identifiers.

Examples:

- Surah 67, ayah 1 → Surah 67, ayah 5.
- Juz 30: Surah 78, ayah 1 → Surah 114, ayah 6.

Do not store only a free-text description such as "Surah Al-Mulk first five verses" as the authoritative reference.

## 9.1.1 Selecting passages

Teacher feedback confirms that teachers mainly track students by surah. The surah and ayah selector is therefore the primary, default selection method and must be the fastest path. Page, juz, and hizb selection are secondary options for teachers who prefer them.

Teachers must be able to select a passage by:

- Surah and ayah.
- Page number.
- Juz.
- Hizb or quarter-hizb.

Whatever the selection method, the system must convert the selection into a canonical ayah range for storage. Displays may show the passage in the teacher's preferred format (for example, "pages 10–12" or "Juz 30").

## 9.2 Quran metadata

Use a reliable, appropriately licensed Quran metadata source.

Include:

- All 114 surahs.
- Correct Arabic surah names.
- English transliterations or translations where appropriate.
- Number of verses in each surah.
- Page, juz, and hizb mapping for every ayah.
- Validation of verse ranges.

### Mushaf and riwayah

Ayah counts and page numbers differ between riwayat and Mushaf printings (for example, Hafs and Warsh).

- The default is the Hafs ʿan ʿĀsim riwayah with the standard Madani Mushaf (604 pages).
- Store the riwayah/Mushaf as an organization setting so other options can be added later.
- Do not mix data from different riwayat in the same reference set.

Store canonical metadata in the database or application data files with documented provenance and licensing.

Do not depend on an external API for every dropdown interaction.

## 9.3 Reference validation

The system must reject:

- Invalid surah numbers.
- Ayah numbers below 1.
- Ayah numbers beyond the surah's actual verse count.
- An ending point that comes before the starting point.
- Invalid page, juz, or hizb numbers.
- Invalid or inconsistent Quran references.

The application should allow teachers to select passages through searchable surah, ayah, page, juz, and hizb selectors.

Avoid requiring teachers to type Quran references manually.

# 10. Memorization Management

This is the core feature of the application.

## 10.1 Record a memorization lesson

A teacher should be able to open a student profile and record a lesson using a fast, simple form.

Required fields:

- Student.
- Lesson date.
- Passage (starting surah and ayah, ending surah and ayah; selectable by ayah, page, juz, or hizb).
- Performance result.
- Teacher or recording user.

Optional fields:

- Accuracy score.
- Number or category of mistakes.
- Fluency assessment.
- Tajweed assessment.
- Teacher comments.
- Whether the lesson meets the completion criteria.
- Next memorization assignment.
- Next revision assignment.

The system should automatically record:

- Organization.
- Recording user.
- Creation timestamp.
- Last update timestamp.
- Record status.

## 10.2 Performance assessment

Use configurable assessment categories, such as:

- Excellent.
- Very good.
- Good.
- Needs improvement.
- Not completed.

Allow organizations to configure the wording later.

Do not treat these labels as objective measurements of Quran mastery. They are teacher assessments.

If a numerical score is enabled, document its scale and meaning.

## 10.3 Mistake tracking

Allow teachers to record useful information about mistakes, such as:

- Forgotten words.
- Sequence mistakes.
- Pronunciation issues.
- Tajweed issues.
- Hesitation.
- Other teacher-defined observations.

Avoid creating an unnecessarily complicated scoring system in the first release.

The teacher must remain responsible for evaluating actual recitation.

## 10.4 Editing and correcting records

Teachers may correct authorized records.

Requirements:

- Preserve the original creation timestamp and creator.
- Record the last editor.
- Keep a history of important changes.
- Do not silently erase completed lesson history.
- Require a reason for sensitive administrative corrections where appropriate.
- Provide an audited soft-deletion or correction workflow instead of uncontrolled permanent deletion.

## 10.5 Batch recording

Support a later enhancement that allows teachers to record lessons for multiple students in a class.

This must not compromise student-specific assessments or create accidental duplicate records.

The first version should prioritize a reliable individual-student workflow.

# 11. Memorization and Revision Assignments

New memorization and revision must be separate concepts.

A student may be learning new verses while revising older passages.

Both kinds of assignment share almost the same fields, so they are stored in one `assignments` table with an `assignment_type` of `memorization` or `revision` (see Section 19). They must still be shown, counted, and reported separately.

## 11.1 New memorization assignment

Fields:

- Student.
- Assigned by.
- Passage (starting surah and ayah, ending surah and ayah).
- Assigned date.
- Due date, optional.
- Instructions, optional.
- Status.

Possible statuses:

- Assigned.
- In progress.
- Student reports completed.
- Teacher verified.
- Needs further practice.
- Cancelled.

Do not automatically mark an assignment as teacher-verified merely because the student marks it complete.

## 11.2 Revision assignment

Fields:

- Student.
- Passage (starting surah and ayah, ending surah and ayah). A revision passage may span several surahs, pages, or a full juz.
- Assigned date.
- Due date, optional.
- Priority, optional.
- Teacher instructions.
- Status.
- Completion and verification timestamps.

Revision may cover previously memorized passages from several surahs. A single revision assignment may cover a cross-surah range such as a full juz; several separate passages may be assigned as several assignments.

## 11.3 Next assignment workflow

After recording a lesson, the teacher should be able to:

1. Save the completed memorization record.
2. Assign the next passage.
3. Assign one or more revision passages.
4. Add a note.
5. Save all changes.

The application should offer suggested next verses, but the teacher must be able to modify or override them.

### Example

If the student completed Surah 67, verses 1–5, the system may suggest verses 6–10 as the next passage.

The suggestion is valid only if the teacher confirms it and the reference is valid.

The system must not assume that every student should progress sequentially or that a particular passage is appropriate for every student.

## 11.4 Assignment history

Every assignment must have a clear history.

The system must distinguish between:

- The original assignment.
- Changes to the assignment.
- Student-reported completion.
- Teacher verification.
- Cancellation.
- Reassignment.

A student's historical assignment must not be overwritten merely because a new assignment is created.

# 12. Revision Planning and Recommendations

Revision is an important part of Quran memorization.

The system should help teachers identify passages that need attention without pretending to assess recitation automatically.

## 12.1 Initial revision functionality

Include:

- Manual revision assignments.
- Revision history.
- Outstanding revision tasks.
- Overdue revision tasks.
- Teacher notes.
- A list of previously memorized passages.
- A way to assign a previous passage again.

## 12.2 Future revision recommendations

A later version may suggest passages based on:

- Time since last revision.
- Teacher assessment.
- Previous mistake categories.
- Incomplete assignments.
- Teacher-defined revision schedules.

These suggestions must be explainable and editable.

Do not describe a passage as "forgotten" solely because its revision is overdue.

Do not introduce complex machine learning in the initial version.

# 13. Parent Portal

The parent portal is one of the primary differentiating features of the product.

## 13.1 Parent dashboard

Display:

- Linked children.
- Each child's current class.
- Assigned teacher.
- Recently completed memorization.
- Next memorization assignment.
- Pending revision.
- Recent teacher feedback.
- Progress over time.
- Attendance, if enabled.
- Important notifications.

## 13.2 Multiple children

A single parent account may be linked to several children.

The parent must be able to switch between children without signing out.

The application must verify the relationship for each child independently.

## 13.3 Parent access boundaries

Parents must see only information explicitly permitted for the linked child.

Do not expose:

- Internal administrative notes.
- Private notes intended only for teachers.
- Other students' records.
- Other families' contact details.
- Internal moderation or security records.
- Organization-level information unrelated to their children.

Separate parent-visible feedback from teacher-only notes.

## 13.4 Parent activation

Parent activation must be optional.

Teachers can manage a student even if the parent has not registered.

The system may display:

- Parent invitation not sent.
- Invitation sent.
- Invitation accepted.
- Invitation expired.
- Invitation revoked.

The teacher should be able to share a parent invitation link directly through WhatsApp or a QR code (see Section 6.3).

Do not block normal lesson recording because a parent account has not been created.

## 13.5 Parent notifications

Notifications may include:

- A new lesson has been recorded.
- A new assignment has been created.
- A revision task is due.
- A teacher has added parent-visible feedback.
- An attendance event has been recorded, if enabled.

Notifications should not include unnecessary personal details in email subject lines or push notification previews.

Parents should be able to manage non-essential notifications.

# 20. Security and Row Level Security

Security is a release-blocking requirement.

The application contains children's educational records and must be designed with privacy as a core concern.

## 20.1 General security principles

- Use Supabase Auth for authentication.
- Use RLS for database access protection.
- Use server-side authorization for sensitive operations.
- Validate all input on the server.
- Use parameterized queries and safe database APIs.
- Never trust client-supplied roles.
- Never trust client-supplied organization IDs without verifying membership.
- Never expose privileged service-role keys to browsers.
- Keep secrets out of source control.
- Use secure production environment variables.
- Apply rate limits to sensitive endpoints and invitation workflows.
- Avoid exposing unnecessary data through errors.
- Maintain an audit trail for sensitive operations.

## 20.2 Row Level Security requirements

Enable RLS on all tables accessible through client-facing database APIs.

Policies must be designed around verified identities and authorized relationships.

Examples:

- A teacher can read students currently assigned to them within the relevant organization.
- A parent can read only data for children linked through a verified, active relationship.
- An organization administrator can manage only authorized data belonging to that organization.
- A student can read only their own permitted records.
- An unauthenticated user cannot read private student data.
- A user cannot grant themselves organization membership or elevate their role.

For operations requiring elevated server privileges, validate the user, organization, role, and record relationship before executing the operation.

Do not assume that server-side code is automatically safe merely because it runs on the server.

## 20.3 Cross-tenant protection

Write explicit tests that attempt to:

- Read another organization's students.
- Modify another organization's records.
- Assign a teacher from one organization to an unauthorized class in another.
- Link a parent to an unauthorized student.
- Guess student IDs and access private profiles.
- Reuse expired invitations.
- Accept revoked invitations.
- Escalate an ordinary teacher account to administrator.
- Access data after a membership or parent relationship has been revoked.

All these attempts must be denied.

## 20.4 Security-sensitive operations

Implement secure workflows for:

- Invitation creation and acceptance.
- Organization membership changes.
- Role changes.
- Parent-child linking.
- Student transfers.
- Account deletion.
- Data export.
- Administrative corrections.

Use transactions and appropriate audit records for multi-step operations.

## 20.5 Privacy requirements

Collect the minimum amount of personal information necessary.

Provide a clear privacy policy describing:

- What information is collected.
- Why it is collected.
- Who can access it.
- How long it is retained.
- How users can request correction or deletion.
- How account deletion affects educational records.
- How third-party services process data.

Review applicable Canadian privacy requirements and any relevant requirements in other jurisdictions before launching.

Do not assume that parental consent or child privacy requirements are identical in every country.

# 23. Performance and Scalability

The application should be designed for growth without unnecessary infrastructure.

Initial design target:

- Support a small pilot with a few organizations.
- Remain responsive as the number of students and historical records increases.
- Support several hundred organizations as a future design goal.
- Avoid full-table scans for routine dashboards.
- Use pagination for large tables.
- Use appropriate indexes.
- Avoid fetching all student records when only a summary is required.

These are design goals, not guarantees of capacity. Actual performance depends on hosting, database sizing, query patterns, and workload.

## 23.1 Data access

- Fetch only the columns required.
- Paginate student lists and lesson histories.
- Apply filters on the server or database.
- Avoid N+1 query patterns.
- Use aggregation queries for dashboard statistics.
- Add caching only when appropriate and safe.
- Ensure cached responses cannot expose data across organizations or users.

## 23.2 Reliability

- Handle database and network failures.
- Avoid duplicate records caused by repeated submissions.
- Mosque internet is often weak. Keep an unsaved lesson form as a local draft on the device, show a clear "not saved yet" state, and retry when the connection returns.
- Send an idempotency key with each lesson and assignment save so that retries never create duplicate records.
- Full offline mode is a future enhancement, not part of the MVP.
- Use idempotent operations where appropriate.
- Use transactions for multi-step writes.
- Provide clear error messages without exposing internal secrets.
- Define backup and recovery procedures.
- Test database migrations before production deployment.

1. Create Organization A and Organization B.
2. Add teachers and students to both.

4. Confirm that every unauthorized operation is denied.

# 28. Important Product Decisions and Rules

Implement the following rules consistently:

1. A parent account is optional.
2. A student can have multiple authorized parents or guardians.
3. A parent can have multiple linked children.
4. A teacher can belong to multiple organizations.
5. A teacher can teach multiple classes.
6. A class can have multiple teachers if authorized.
7. A student can move between classes without losing history.
8. Historical records retain their original creator and timestamps.
9. New memorization and revision are separate concepts.
10. Student-reported completion is different from teacher verification.
11. The teacher controls the final memorization assessment.
12. Organization isolation is enforced at the database and server levels.
13. Parent access requires a verified relationship.
14. Role changes and sensitive corrections are auditable.
15. Quran references are validated against canonical metadata.
16. No public page exposes private student records.
17. No advertising feature may depend on access to student educational records.
18. The system must remain useful without a student account.
19. The system must remain functional if notifications fail.
20. All important workflows must be testable.
